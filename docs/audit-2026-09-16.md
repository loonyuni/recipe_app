# Code audit & cleanup plan — 2026-09-16

Snapshot of the codebase after the browsing/theme/photos work, with a prioritized
cleanup plan. Guiding principle: this is a **static-first personal app on free
GitHub Pages with no build step**. Keep it that way. Reach for structure that
improves maintainability without adding a bundler/framework/CI burden.

## Current state

- `app.js` — 2,834 lines, 128 functions, one file. Everything: state, Supabase
  load/sync, rendering (grid + detail), routing, import flow, auth, theme,
  storage upload.
- `styles.css` — 512 lines in **two layers**: the original warm-paper theme
  (1–368) and an appended "editorial" override block (370+) that re-skins it.
- `index.html` — 387 lines, includes inline Lucide `<symbol>` defs.
- 8 loose `supabase-*.sql` migrations at repo root; 1 edge function.
- 7 loose markdown docs at root (README, AGENT, CHANGELOG, ENHANCEMENTS,
  QA_USER_STORIES, CODEX_IMPORT, SUPABASE_SETUP).
- No test suite (only `node --check` + an ad-hoc DOM harness during this work).
- Deploy = merge to main; **manual `?v=` cache-bust** required each time.

## What's good (leave alone)

- Static-first, zero-build, loads fast off the CDN. Don't add a bundler.
- Clean security model: anon reads a definer view, writes are always authed.
- Token-driven CSS makes re-theming cheap.
- Free-tier-savvy: localStorage SWR + CDN snapshot sidestep cold starts.

## Findings (tech debt), by priority

### High
1. **CSS dual-layer.** The editorial theme is bolted on top of the warm-paper
   base with overrides fighting the originals. Hard to reason about; dead warm
   values (`--paper #f5f0e7`, sage/yellow, Fraunces/Manrope/DM Mono) linger.
   → Consolidate into one token set + component rules; delete the dead theme.
2. **`app.js` monolith (2.8k lines).** Slow to navigate and edit safely; easy to
   introduce cross-talk. → Split into native ES modules (no bundler): e.g.
   `src/state.js`, `src/supabase.js`, `src/recipes.js` (load/sync), `src/render.js`
   (grid), `src/detail.js`, `src/import.js`, `src/auth.js`, `src/photos.js`,
   `src/theme/tokens` (CSS). Load via `<script type="module">` — works on Pages.

### Medium
3. **Repeated markup in JS template strings.** Cards, labels, meta, buttons, and
   the detail sections are hand-built inline. → Extract small render helpers
   (`card(recipe)`, `label(text)`, `iconButton(...)`) to cut duplication and make
   the "component library" real without a framework.
4. **Loose SQL at root.** 8 migrations with no ordering/version record. → Move to
   `supabase/migrations/NNNN_*.sql` (numbered), keep a short index. Optional:
   adopt the Supabase CLI migration flow.
5. **Manual cache-bust.** Every deploy needs a hand-edited `?v=`. → A tiny service
   worker (network-first for HTML, cache-first for hashed assets) removes the
   ritual and auto-updates the installed PWA. Or a pre-commit hook that stamps
   the version.

### Low
6. **Dead code.** `copyShareLink` is unused since the Share button. Prune.
7. **Doc sprawl.** 7 root markdowns overlap. → Fold into README + CLAUDE.md +
   `docs/`; retire stale ones (CODEX_IMPORT, QA_USER_STORIES if obsolete).
8. **`supabase-config.js` is committed** (publishable key — safe, but README says
   it's gitignored). Reconcile: either gitignore it and ship `.example` only, or
   document that the publishable key is intentionally public.
9. **No tests.** For a personal app, a small smoke test (the DOM harness,
   committed) + `node --check` in a GitHub Action would catch regressions cheaply.

## Recommended plan (tiered — pick a stopping point)

- **Tier 1 — docs (done in this pass):** add `CLAUDE.md`; this audit. Low risk.
- **Tier 2 — cleanup, no restructure:** consolidate CSS into one token system
  (remove dead warm theme), prune dead code, extract a few render helpers, tidy
  docs. Same files, cleaner. Moderate effort, low risk.
- **Tier 3 — structure:** split `app.js` into ES modules; move SQL to
  `supabase/migrations/`; optional `src/` layout. Biggest maintainability win,
  but real churn (every reference + cache-bust) and regression risk — and it
  needs an in-browser pass to verify, which the agent can't currently run.
- **Tier 4 — automation (optional):** service worker for auto-update; a GitHub
  Action running `node --check` + smoke test; snapshot regeneration on a schedule.

## Recommendation

Do Tier 1 now (this commit). Then Tier 2 (real cleanup, low risk) is the best
value. Hold Tier 3 (module/dir restructure) until there's a way to verify it in a
real browser, and only if active development continues — a working static app
doesn't need it to function. Avoid bundlers/frameworks entirely.
